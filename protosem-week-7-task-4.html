01Overview

The objective is a login-protected web dashboard that reads live data — temperature, humidity, ambient light and device status — from a Firebase Realtime Database and can write a bulb control command back. This task is the cloud/dashboard half of the system: it builds the database, the authentication, and the page that reads and writes to it. Getting a physical sensor or ESP32 actually writing that data is a separate, later task — here the dashboard is built and proven against the database itself.

02Concepts

Cloud computing

Using computing resources, storage and services over the internet instead of owning the hardware.

IaaS, PaaS, SaaS, BaaS

IaaS rents raw servers and storage. PaaS gives a platform to run your own code. SaaS is finished software you just use. BaaS supplies ready-made backend features such as database and login; Firebase is BaaS.

Cloud platform and database

A cloud platform hosts services for you. A database stores structured data so it can be saved and read back later.

Firebase Realtime Database

A cloud database stored as JSON that pushes changes to every connected client instantly, so the dashboard updates live as soon as a value changes.

Cloud-based dashboard

A web page that reads live data from the cloud and shows it, with controls to send commands back.

Authentication vs Authorization

Authentication proves who you are (login). Authorization decides what you may do (database rules).

03System Design

Firebase Realtime Database⇄Login dashboard

The dashboard listens live on sensors and status and renders whatever is there; it writes to control when the mode or bulb toggle is changed. A separate device writing into sensors/status and reading control is what a later task connects — this task only has to prove the dashboard side works correctly against the database.

05Implementation

Explain these key sections in your own words:

  • Firebase web SDK config and initialization — the dashboard loads the Firebase app config generated when the env-monitor-web app was registered, and initializes Auth and the Realtime Database on page load before anything else runs.
  • Login page — a separate sign-in screen sits in front of the dashboard; signInWithEmailAndPassword checks the entered credentials against the Email/Password users created in Authentication, and only a successful sign-in redirects into dashboard.html.
  • Live listeners on sensors and status — onValue() listeners on those two nodes update the Temperature, Humidity and Ambient Light (LDR) cards the instant a value changes, and flip the "Device offline" banner based on status; with nothing writing to either node yet, the cards correctly sit at -- and the banner stays red.
  • Mode toggle and bulb switch — the Manual/Auto switch and the Bulb on/off switch both write straight to control the moment they're flipped, so the dashboard's own UI state and the database stay in sync regardless of what (if anything) is listening on the other end.
  • Historical Data table and CSV export — the table is driven by a query against logs (indexed on timestamp) and shows "Loading..." until rows arrive; the Download CSV button serializes whatever rows are currently loaded into a file.

06Configuration

  1. In the Firebase console, chose Get started by setting up a Firebase project, named it env-monitor (auto-assigned project ID env-monitor-845af), accepted the Firebase terms, kept Gemini in Firebase enabled, set the Analytics location to India with the default data-sharing settings, and created the project
  2. Checked prerequisites in a terminal: node --version (v24.21.0, installed via the Windows installer), then installed the CLI with npm install -g firebase-tools
  3. Ran firebase login, which opens a Google OAuth consent screen; signed in with the project's Google account and declined the optional Gemini-in-Firebase and CLI usage-reporting prompts
  1. From the project folder, ran firebase init hosting, chose Use an existing project and selected the existing env-monitor-845af (env-monitor) project rather than creating a new one
  2. Kept . as the public directory, declined single-page-app rewrites and GitHub auto-deploy, and chose not to overwrite the existing index.html
  3. Deployed with firebase deploy; the CLI uploaded the files and returned the live Hosting URL env-monitor-845af.web.app
  1. In Authentication → Sign-in method, enabled the Email/Password provider, then added users from Authentication → Users → Add user so only signed-in accounts can reach the dashboard
  2. In Realtime Database, created the database in the us-central1 (United States) location, starting in locked mode (all reads/writes denied by default), then registered a Web app (env-monitor-web) under Project settings to get the SDK config for the dashboard
  3. Replaced the default locked rules with rules scoped to four top-level nodes, all gated on auth != null:
{
  "rules": {
    "sensors": {
      ".read": "auth != null",
      ".write": "auth != null"
    },
    "control": {
      ".read": "auth != null",
      ".write": "auth != null"
    },
    "logs": {
      ".read": "auth != null",
      ".write": "auth != null",
      ".indexOn": ["timestamp"]
    },
    "status": {
      ".read": "auth != null",
      ".write": "auth != null"
    }
  }
}

sensors holds the live readings the dashboard displays, control holds the bulb mode/state the dashboard writes (and a future device would read), logs is the timestamp-indexed history behind the CSV export, and status is what drives the dashboard's "Device offline" indicator.

08Challenges & Fixes

  • Locked-mode rules denied everything by default — starting the Realtime Database in locked mode sets ".read": false, ".write": false globally, so the database would have rejected the dashboard even after login. Rather than switching to open test-mode rules (which expire and allow anyone to read/write), I wrote explicit per-node rules for sensors, control, logs and status, each gated on auth != null, so access opens up only for signed-in users and nothing is ever public.
  • Almost overwrote the existing dashboard — firebase init hosting detected an index.html already in the folder and prompted to overwrite it. Saying No kept the hand-built dashboard intact; the CLI just added 404.html, firebase.json and .firebaserc alongside it instead of touching the existing page.
  • Picking the right project during init — because the env-monitor project already existed in the console from the earlier setup step, firebase init hosting had to be pointed at Use an existing project rather than Create a new project, otherwise the CLI would have spun up a second, disconnected Firebase project with no Auth users or database rules in it.
  • Multiple Google accounts in the login chooser — firebase login opens the standard Google account picker, and with several accounts signed into the browser it was easy to authorize the wrong one. Selecting sachinsivapragash@gmail.com specifically kept the CLI, the console project and the Auth users all under the same identity.
  • Dashboard shows "Device offline" with blank readings — the hosting, login and database rules are all live and working, but nothing is writing to sensors/status yet, so the UI correctly has nothing to render. Feeding real values into those nodes is a separate, later task; here the dashboard just needs to reflect whatever is actually in the database.

09Reflection

The biggest shift from the earlier tasks is what "backend" means here. Tasks 2 and 3 leaned on Adafruit IO feeds that were open the moment I created them — anyone with the feed key could read or write. Firebase starts from the opposite default: a brand-new Realtime Database locks every read and write until you explicitly say otherwise, which forced me to actually think about who should be allowed to touch what, node by node, instead of trusting one shared key for everything.

That's really where authentication and authorization stopped being interchangeable words for me. Authentication is just Firebase confirming who's signed in — the Email/Password provider and the Users list handle that part entirely. Authorization is the separate question the rules file answers: an authenticated user can read sensors and write control, but the rule itself doesn't care which authenticated user it is, only that auth != null. Splitting the database into sensors, control, logs and status instead of one flat tree also made the rules easier to reason about — each node can eventually get its own, narrower policy without touching the others.

Right now the project is deployed end-to-end on the cloud side — hosting, login, and a database with real security rules — and the dashboard correctly shows "Device offline" because nothing is writing to it yet. That's an honest, working state for this task: proving the database and dashboard behave correctly on their own, before any device is connected to them.
